# 食刻：food_ordering 连锁餐饮产品设计 v1

**日期：2026-11-05｜状态：设计提案，待评审；不是已实现功能清单。**

设计基线：公开仓库 `zhaoawd/food_ordering` 的部分 `main` 文件。读取了依赖、首页、导航、购物车、优惠券、观测协议及测试；本环境没有成功克隆整个仓库，未锁定 commit SHA，未构建或运行原生应用。实施任务 A00 必须先冻结真实代码基线。来源编号见文末及 `source-audit.json`。

## 1. 产品方向与范围

目标不是把首页换成肯德基的红色，而是形成“门店与用餐方式 → 可售菜单 → 商品及套餐 → 购物车 → 优惠报价 → 支付 → 制作/配送 → 会员复购”的闭环。肯德基官方 App 商店说明列出了自助点餐、外送、优惠、会员权益及 AI 点餐等能力；这里只参考公开的能力分类，没有宣称审查其完整线上交互或内部架构。[S10–S11]

品牌采用暂定独立概念 **食刻 / FRESH MOMENTS**，延续现有项目暖色基调。品牌名、商品插画、门店、价格及积分均为设计样例；不是肯德基商品、官方视觉或正式商业规则。上线前需确认品牌、素材授权及真正的商品/过敏原资料。

主要用户：午餐自取用户、需要稳定配送的家庭用户、使用优惠券的复购用户。优先目标：选对门店、价格可解释、不会重复支付、订单状态可信、失败可恢复。反目标：先堆活动入口，后补交易一致性；把 AI 推荐当作真实可售性判断；用 App 自报的成功替代外部验证。

### 方案比较与推荐

| 方向 | 优点 | 代价/问题 | 本稿结论 |
|---|---|---|---|
| 仅改 UI、继续本地状态 | 演示快 | 不能证明真实订单和支付，难称连锁餐饮产品 | 仅用于交互稿 |
| 保留 RN/Expo，渐进补齐领域契约 | 复用现有代码和验证资产，可按纵向流程验收 | 需要新增交易后端及环境隔离 | **推荐；本次设计假设，尚非用户确认的实施决策** |
| 重写原生或一次性做完整超级 App | 可自由设计 | 迁移与验证成本高，偏离已有资产 | 当前不推荐 |

P0 完成可验收的自取业务骨架，支付和厨房由测试适配器模拟；P1 加入配送、会员与售后；P2 再做 AI、付费权益和增长实验。真实支付上线、正式发布、隐私法务和退款运营需独立评审，不因 P0 测试成功而自动放行。

## 3. 功能路线

### P0：自取交易闭环

F01 游客浏览、登录后恢复购物车；F02 首页/点餐/优惠/订单/我的真实导航；F03 门店与渠道；F04 门店菜单与搜索；F05 套餐规格；F06 购物车；F07 优惠券；F08 服务端报价；F09 模拟支付与查单；F10 订单与取餐；F11 数据化验收；F12 自适应与无障碍。

P0 不能省略的异常：定位拒绝、店休、售罄、必选缺失、数量上限、换店冲突、券失效、报价过期、变价、库存竞争、重复提交、支付未知、重复/乱序回调、前后台切换、网络失败、折叠时键盘焦点。

### P1：履约与复购

F13 外送：地址与配送范围、起送额、配送费、时段容量、配送状态；F14 会员：身份、积分账本、权益与核销；F15 运营配置：活动、优惠、菜单推荐位；F16 收藏/再来一单；F17 退款售后；F18 消息；F19 评价客服；F20 隐私账号。

会员积分不能只是一列可任意累加的余额。用不可变账本记录获取、消费、退款冲正、过期，关联业务事件去重。退款是否退券、退积分、退配送费必须有独立版本化策略，不能由客户端猜测。

### P2：增强能力

F21 AI 选餐：读取实时菜单与预算/偏好约束，返回受 schema 约束的商品 ID 和规格，服务端再校验，用户确认后加购；不自动扣款。F22 付费会员：先做单次购买、明确有效期的权益卡，不默认做储值和自动续费。F23 预约早餐/团餐：容量、截止时间与取消政策。F24 推荐与实验：分组固定、可停用、保留普通点餐入口。

## 4. 信息架构与页面职责

底部导航固定为 **首页｜点餐｜优惠｜订单｜我的**。商品详情、购物车、结算、支付属于交易栈。登录、地址、退款等采用独立路由或系统弹层；本版高保真稿不覆盖全部后续表单。

| 页面 | 核心内容 | 主操作 | 状态重点 |
|---|---|---|---|
| 首页 home | 门店、用餐方式、活动、人气商品、会员、进行中订单 | 开始点餐/继续订单 | 游客、加载、网络错误 |
| 门店 stores | 手动搜索、定位、营业状态、距离、渠道 | 确认门店 | 权限拒绝、店休、换店冲突 |
| 点餐 menu | 门店上下文、分类、搜索、可售商品、购物袋摘要 | 选商品/开购物袋 | 售罄、无结果、过餐期 |
| 商品 product | 套餐构成、必选组、规格加价、数量、过敏原 | 加入购物袋 | 必选未完成、售罄、数量上限 |
| 购物车 cart | 稳定行键商品、规格、费用、优惠 | 去结算 | 空态、失效项、券失效 |
| 优惠 coupons | 可用券及原因、草稿选择、确认/取消 | 应用优惠 | 不满足门槛、时效/门店限制 |
| 结算 checkout | 门店确认、取餐时间、订单备注、完整费用 | 提交订单 | 未登录、报价失效、价格变化 |
| 支付 payment | 订单号、确认金额、支付状态 | 支付/查询原支付 | pending、unknown、失败 |
| 订单详情 order | 制作/配送时间线、取餐码、费用与售后 | 取餐/查进度/售后 | 准备中、可取、完成、取消 |
| 订单列表 orders | 进行中及历史订单 | 查看进度/再来一单 | 空态、重下单商品失效 |
| 我的 member | 会员身份、券、积分、地址、偏好、隐私 | 查看权益/服务 | 未登录、权益/积分变更 |
| 地址 address | 地址簿、配送范围与隐私 | 确认配送地址 | 范围外、输入错误 |
| AI ai | 用户约束、结构化推荐、依据与确认 | 确认套餐 | 无可用匹配、数据陈旧 |

完整状态定义在 `spec/screens.json`；71 个状态是规格与 fixture 配方，**不是71张已绘制高保真页面，也不是71个已实现原生状态**。

## 5. UI 与交互规范

视觉：暖白背景 #FAF7F2，强调色 #C93C25，深棕正文 #251D19，绿色只表达可信的成功/营业状态。采用大留白、食品插画、可读金额和少量营销层级。使用原创矢量示意图而不是冒用品牌商品图；上线时替换为经过授权且符合真实 SKU 的图片。

尺寸：以390×844逻辑点展示手机稿，760×844展示宽屏稿；这些是设计画布，不是声称某硬件实际逻辑分辨率。主要 CTA 高52pt，交互目标至少44pt，正文15pt、辅助13pt，中文和英文价格长文本均允许换行。应用使用系统字体；Figma 使用可用中文字体替代，像素级字体差异需在目标系统校准。颜色、间距、圆角和断点在 `design-tokens.json`。

行为：主按钮固定于安全区上方，内容独立滚动；敏感信息不进入默认截图；颜色不是唯一状态提示；读屏标签为用户文案，不把开发 stable_id 当 accessibilityLabel。选择规格后保留焦点，返回列表保留分类和滚动位置。弹层打开/关闭需恢复到正确的触发控件。

商品卡显示明确基础价/起价。加价只影响对应规格；必选数量、售罄等错误在组附近显示，不依赖稍纵即逝的 Toast。结算页明确提示实际门店并要求确认。换店、换渠道和换地址先展示冲突及差价，用户确认后应用，不静默丢弃购物车。

### Duo / 宽屏

依据当前容器测量到的**可用逻辑宽度**布局，不依据设备名或物理像素。`useWindowDimensions` 可以响应窗口及字体变化，但还需扣除实际安全区、分栏容器和系统占用；既有 RN 版本可用性由实现核实。[S12]

小于600pt单栏；600–839pt在可满足最小栏宽时使用菜单+购物袋或列表+详情；840pt以上仅在菜单、详情、购物袋最小宽度加间隔均满足时考虑三栏。字体显著放大时回退单栏。断点是初始设计参数，需目标设备验证，不是硬件规范。

业务状态只有一份：store_id、channel、cart、selectedProduct、optionDraft、quote、orderId。界面切换只是不同的投影。展开/折叠、横竖屏、输入法显示、后台恢复不得清空购物车或再次提交订单。验证必须特别包含“输入框聚焦→展开→收起→继续输入→结算”的完整链路。

## 6. 数据和业务规则

领域实体至少包括 User、Store、MenuVersion、Product、OptionGroup、StoreAvailability、Cart/CartLine、CouponDefinition/UserCoupon、Quote、Order/OrderLineSnapshot、PaymentAttempt、Refund、FulfillmentEvent、LoyaltyLedger、Campaign、AuditEvent。实体关系与归属见 `domain-model.json`。

金额一律用整数分和明确 currency，不能使用显示文本反算。前端显示报价，不能在创建订单时自报可信 payable。订单行保存购买时名称、规格、单价及规则版本快照，不能引用会变化的商品数据生成历史订单。

### 固定测试样例

标准鸡腿堡套餐3290分×2=6580分；包装400分；自取配送0分；满60减10扣1000分，**应付5980分（¥59.80）**。相同样例外送费300分，则应付6280分。优惠门槛仅用券可优惠商品金额，不把打包/配送费计入；P0 每单至多一张订单券，不叠积分抵扣。

旧仓库规则作为 `legacy-v1` 保留：两份3200分商品、包装400、配送300、减1000，应付6100。新 `commerce-v1` 的 save6 门槛3900与旧3200明确区分。不能为新 UI 修改旧 fixture 让历史测试“变绿”。

### 报价到订单

Quote 绑定用户、门店、渠道、购物车摘要、价格版本及过期时间。120秒只是提议的初始 TTL，不意味着价格可在这段时间无条件锁定库存。提交时服务端再次校验。库存/券预占、订单创建用事务或具有补偿与 outbox 的流程获得一致效果。券不可多单并发核销；库存不能靠客户端缓存保证。

创建订单使用 user+operation+idempotency_key 唯一约束；同key同请求返回同结果，同key不同请求拒绝。客户端禁用按钮只改善体验，不替代后端幂等。订单、支付、退款为三个状态机；支付成功后退款不把 payment 倒退成 failed。

支付 timeout 标记 unknown，先查原订单/支付尝试，不创建另一笔订单。服务端验证回调签名、商户订单、归属、金额、币种，去重重复事件。迟到成功回调落到已取消/过期单，应进入对账与补偿退款路径，不能自动恢复制作。真实网关接入前，测试适配器必须能重放这类事件。

取餐码只能在支付被服务端确认并进入可信履约阶段后出现；不能因为客户端计时器结束而显示。再来一单必须重新校验可售性、规格、价格和优惠。

## 7. 架构落地与非用户端依赖

客户端保留 Expo Router + Zustand，逐步把页面大块拆成展示组件、领域 store/selector、服务接口和测试适配器。不要把网络请求、金额引擎、导航与 UI 放进同一组件。既有 Appwrite SDK 可继续承担已验证合适的身份/资料/存储用途，但不能据“安装了SDK”就断言已具备可靠交易事务。

建议接口由服务端统一报价与订单服务提供。`api/openapi.json` 是核心交易的建议契约，不是已部署服务，也不是全部后端范围；地图、真实网关、门店厨房、物流、短信、活动发布后台、会员核销和会计对账均需单独接入。

门店/运营侧最小能力：维护营业时间与临时闭店、菜单上下架/售罄、可售时段和渠道、价格版本、接单/制作/叫号、取消/退款审核、券批次与权益发布、权限审计。P0 用独立测试管理适配器模拟，不能在普通消费者 App 隐藏菜单里直接改生产订单状态。

活动 JSON 只允许白名单模块（Banner、CategoryEntry、ProductShelf、CouponEntry、MemberCard、OrderResume），引用受控数据和已注册路由。配置要有版本、有效期、门店/渠道范围、预览、灰度、回滚和默认兜底。不得把任意 JS 或不受控远程代码当“数据化”。

## 8. Agent 工作契约

**唯一事实来源应分层：**业务与接口规格决定逻辑，设计 token 与页面结构决定展示，服务端报价决定真实金额，批准的独立测试预期决定验收。Figma/HTML是对规格的可视表达，不是允许随意改写金融规则的来源。

引用链：feature_id → screen/state → fixture → control stable_id → source_ref → API/event → test_id → evidence。结构化文件维护版本及 SHA；JSONSchema、外键、任务 DAG、固定金额由校验脚本检查。

角色建议：Planner 仅拆任务；Builder 在允许路径内实现；QA 根据冻结规格验证而不是跟着实现改预期；Reviewer 处理规则、golden和迁移审批；Release 管理真实支付/发布权限。权限是真正的工具/凭证隔离，不能只靠提示词写“不要操作生产”。

每次只做一条可验证纵向能力。任务 A00–A10 给出依赖和允许路径，但这些路径是提案，实施前读实际仓库。产物应包括 diff、功能/控件映射、测试结果、截图、AX树、服务端读回、已知未实现项。先证明失败断言有效再实现，通过后做独立复核；禁止为过测改golden、删除旧测试、直接写Store制造目标状态。

## 9. 验证分层与证据

| 层 | 验证对象 | 必需说明 |
|---|---|---|
| 规格静态校验 | JSON引用、schema、DAG、固定样例 | 本设计包可执行；不证明App正确 |
| 领域单测 | 规格组合、数量、费用、券、状态转移 | 验证边界及不变量 |
| API/集成 | 并发库存/券、幂等、归属、回调、退款 | 必须独立服务端读回与可重放事件 |
| 浏览器交互稿 | 页面可渲染、演示流程、金额一致 | 只验证HTML设计稿，不等同RN Web或iOS |
| iOS模拟器/VM | 真实RN层级、触摸、AX、键盘、前后台、布局 | 需能力探测，不能假设自定义VM支持XCTest/Maestro |
| 真实设备/发布构建 | SDK支付、系统权限、性能、签名、隐私 | 发布门禁，不由VM结果替代 |

保留 `autophone-ui-observation.json` 的定位价值，但它来自应用内部。截图由驱动取，AX树由操作系统/测试框架取，业务结果由只读测试接口取。必须注入“内部JSON宣称成功但实际金额/文本错误”的变异测试，确认评估器能拒绝。只检查稳定ID存在也不够，还要检查可见性、命中范围、可操作状态与最终业务结果。

截图比对固定设备、逻辑大小、系统、字体缩放、locale、时钟、菜单版本、run_id。仅遮罩确有非确定性的区域；金额、CTA、订单状态、门店和取餐码不可被大面积遮罩。baseline由Reviewer批准且不可由Builder自动替换。

所有 run 独立数据命名空间、nonce、账号、订单和设备租约；记录应用二进制SHA、规格SHA、代码SHA、fixtureSHA。设备重置/证据回收失败记为 blocked，不记pass。测试时间推进和seed接口只能存在于验证构建及隔离后端；发布构建应静态/动态验证不可访问。

### VM 池与发布验证

Kubernetes适合负责租约、排队、制品、资源配额与报告；具体iPhone VM仍由具备已验证能力的宿主执行。驱动契约见 `agent/driver-contract.json`，这是抽象接口而非声称现有fork已有这些HTTP端点。探测 install/launch/tap/query/AX/screenshot/fold/reset 等能力。缺能力时切换已支持的驱动或将对应用例标 blocked，禁止回退为坐标乱点后宣称通过。

Maestro 文档给出 RN testID 对应选择器与独立App的 appId；包内 YAML 仅为适配模板，需要实际构建、fixture启动以及服务端断言后才能纳入原生验收。[S13]

## 10. 实施顺序与发布门槛

A00锁定commit与旧测试基线 → A01导航/设计token → A02门店/商品/套餐 → A03购物车/优惠双版本 → A04服务端报价与订单 → A05模拟支付与履约 → A06原生、自适应、验证入口隔离。之后A07配送售后、A08会员隐私、A09运营、A10AI。

推荐第一个完整切片：打开首页→选择营业门店→标准套餐2份→满60减10→确认门店→创建唯一订单→模拟支付确认→制作/取餐。验收同时检查¥59.80、只创建1单、券占用1次、正确取餐状态及可恢复错误。这个切片稳定后再扩展，而不是同时让多个Agent改所有store和路由。

P0发布到内部验证环境的门槛：关键金额/幂等/归属/安全用例全部通过；不允许已知错门店、重复扣款、错优惠；旧测试无未解释回归；目标窗口与大字/键盘回归通过；所有结果都有run证据。真实支付与公开发布另设审批，性能指标在A00测量后设定预算，不把本稿未测量数字包装成已有性能保证。
